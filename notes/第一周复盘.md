## 二、踩过的坑（按疼的程度排）

### 1. `input()` 在 PyCharm 里像卡死了，我把两道练习注释掉了 —— Day 003

写完 `input()` 一运行，光标不动、界面没反应，我以为程序死循环了，直接关掉，然后把整段注释掉。

**真实原因**：程序没死，它在等键盘输入。但 PyCharm 的 Run 窗口不给任何提示，光标不会跳，看起来跟卡死一模一样。

**正确做法**：鼠标点一下 Run 窗口的黑色区域，直接敲数字然后回车。

**教训**：程序"没反应"有两种可能——真卡死了，或者在等输入。先看它有没有在等输入，再判断是不是 bug。

### 2. 建 PyCharm 项目卡了三次 —— Day 001

三次都卡在同一件事：不知道该点 New Project 还是 Open、解释器该选哪个。

**真实原因**：机器上装了三份 Python（D 盘 3.13.15、WorkBuddy 托管的 3.13.12、WindowsApps 的占位符），`python` 命令和 `pip` 指向的不是同一个。选错解释器，装包就会装到别的地方，然后 import 时报"找不到"。

**教训**：**建项目时，解释器路径里必须带 `.venv`。** 看到的是 `D:\develop\python\python.exe` 就说明选错了，那会污染全局环境。

### 3. 变量名拼错 —— Day 004

`16.py` 里写了 `citys`（该是 `cities`），`17.py` 里写了 `lenght`（该是 `length`）。

**疼在哪**：同一个变量如果在两处拼得不一样，程序不会提示"你拼错了"，只会报 `NameError: name 'lenght' is not defined`，然后我得回头一行一行找。

**教训**：变量名就是变量名，不是草稿。拼错一次的代价是半小时。

### 4. 拼音变量名 —— Day 005

`shuju`、`shuru`、`shubiao`。

能跑，但代价是三个月后自己回来看要重新猜一遍。而且这种东西放进项目里，别人一看就知道是新手写的。

**改成什么**：`scores`、`user_input`、`numbers`。名字要说清"它是什么"，不是"它大概是啥"。

顺带一个：`f_1`、`k_1` 这种带编号的变量名，说明当时没想清楚这个变量代表什么。应该叫 `best_score`、`best_name`。

### 5. f-string 里嵌套同一种引号 —— Day 005

```python
print(f"[{m["role"]}]{m["content"]}")   # 外层双引号，内层也是
```

我这台机器能跑，因为 Python 3.12 起放开了这个限制，我装的是 3.13。**但换到 3.11 及以下会直接 SyntaxError。**

**保险写法**：外面双引号、里面单引号，任何版本都能跑。

```python
print(f"[{m['role']}]{m['content']}")
```

### 6. 字典取值用了方括号 —— Day 005

`student["score"]` 这种写法，键不存在时会直接 `KeyError` 让程序崩掉。

**改成 `student.get("score", 默认值)`**，键不存在就返回默认值，程序继续跑。

**教训**：键确定存在才用方括号；不确定一律用 `get`。

### 7. 读文件不写 encoding，PyCharm 里必炸 —— Day 007

同一份代码，终端跑正常，PyCharm 里跑报：

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xaf in position 38
```

**原因**：系统里配了 `PYTHONUTF8=1` 让我在终端里默认走 UTF-8，但 **PyCharm 的运行配置不继承这个环境变量**，于是回落到 Windows 中文版默认的 cp936（GBK）。用 GBK 去读 UTF-8 存的中文文件，读到一半就崩。

**教训**：只要 `open()`，下一件事就写 `encoding="utf-8"`。读要写，写也要写。**"换个地方跑就不一样"的 bug 最浪费时间。**

### 8. `"w"` 打开文件的那一瞬间，内容就没了 —— Day 007

本来想往文件末尾加一行，结果写了 `"w"`。**不是写完才清空，是打开就清空**，而且没法撤销。

**改法**：追加用 `"a"`。

### 9. 一个函数的 return 分支返回了不同类型 —— Day 006

`find_max` 空列表时我 `return "该列表没值"`（字符串），正常时返回数字。看着贴心，但调用方拿去做运算就炸：`TypeError: unsupported operand type(s) for /: 'str' and 'int'`。

**教训**：一个函数的所有 return 分支必须返回同一种类型。取不到值就返回 `None`。

## 五、下周要改的四个习惯

| # | 习惯 | 具体怎么做 |
|---|---|---|
| 1 | **变量名先想再用** | 敲下去之前问一句"它到底是什么"。拼写不确定就查，别猜 |

## 六、几个真实的判断

**1. 进度没有落后，反而超了一点。**
原计划第 1 周只要求"能不看资料写出 100 行脚本、知道报错在哪一行"。我现在能拆函数、能读写文件、能做出 6 个完整程序。**计划的天数用完了，但产出比计划要求的多。**

**2. 我学得慢的部分是有原因的，而且不会再发生。**
Day 001–002 花了将近 3 天，全卡在环境和工具上（建项目卡 3 次、`input()` 以为卡死）。这两天的内容本身不难，难的是"不知道该点哪个按钮"。**这类损耗是一次性的**——环境已经配好，后面不会再回来。

**3. 最有价值的不是语法，是那几个报错。**
`KeyError`、`UnboundLocalError`、`NoneType`、`unhashable type: 'list'`、`UnicodeDecodeError`、`not writable`——这些名字我现在看到不慌了，能猜出大概是什么问题。

这个能力比多背两个语法重要得多，因为**以后写项目 80% 的时间在排错**，而报错信息是唯一的线索。

**4. 我最大的短板不是技术，是"没有真实反馈"。**
一周里所有代码都是我照着文档敲、自己看输出对不对。**没有人 review，没有对比基准，没有真实用户的失败输入。** 这在学语法时够用，但做项目时不够——第 10 周做 RAG 时会有评估集，那时候才知道自己到底行不行。

**5. 我现在离"能投简历"还差很远，但方向是对的。**
目前这些代码，任何一个计算机专业的学生两天就能补完。真正的门槛在后面两个项目（RAG 和 Agent），以及能不能用数据说清"我优化了什么、提升了多少"。**那才是简历上唯一值钱的东西。**
